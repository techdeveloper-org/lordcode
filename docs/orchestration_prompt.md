### Path portability — the absolute paths above are a DEFAULT, not a hardcoded constant

The two paths are written as absolute Windows paths because that is where this project actually lives today, and a dispatched agent needs a concrete path it can act on — a variable name alone is not actionable. But an agent that treats those strings as immutable, or that string-parses them (splitting on `\`, assuming a drive letter, assuming case-insensitivity), breaks the moment this pipeline runs in a Linux container, on macOS, in CI, or under a different user account.

**Resolution order — every agent applies this before using either path:**
1. If the environment variable `LORDCODE_LIBRARY_PATH` / `LORDCODE_PROJECT_PATH` is set and non-empty, **use it and ignore the literal below.**
2. Otherwise, if `LIBRARY_PATH` / `PROJECT_PATH` is set in the environment, use that.
3. Otherwise, fall back to the absolute literal in this document.

**Rules that hold in every environment:**
- Treat both paths as **opaque roots**. Join to them with the platform's own path-joining primitive (Go `filepath.Join`, Python `pathlib` / `os.path.join`, POSIX shell parameter expansion) — never by string concatenation with a hardcoded separator, and never by regex over the path.
- Never assume a drive letter, a `C:` prefix, a backslash separator, case-insensitive matching, or that the two roots share a common parent. They happen to be siblings today; nothing guarantees that.
- Paths RELATIVE to each root — `agents/<name>/agent.md`, `skills/<name>/SKILL.md`, `knowledge-graph/_master/README.md`, `docs/phase-0-requirements/PRD.md` — are stable and portable, and are always written with forward slashes in this document. Those relative fragments are the contract; the roots are configuration.
- If a resolved root does not exist or is not readable, **fail loudly with the resolved path in the error message.** Never silently fall back to `~/.claude/`, `%USERPROFILE%\.claude\`, a default Claude install directory, or the current working directory — a silent fallback here produces an agent that reads the wrong corpus and reports success, which is worse than a clean failure.

**This is also a LordCode PRODUCT requirement, not only pipeline hygiene.** LordCode ships as a cross-platform binary on Windows, macOS, and Linux (amd64 + arm64), so the same discipline applies to the code being built: **every local directory LordCode creates** — the credential fallback store (ADR-4's headless-Linux path), user config, session history, and pipeline state — must resolve through a platform-correct API (`os.UserCacheDir()` / `os.UserConfigDir()` in Go), never a hardcoded `~/.lordcode` or `%APPDATA%` literal; and the CLI must handle paths containing spaces, non-ASCII characters, and UNC prefixes. `business-analyst-agent` writes this as an explicit NFR in Phase 0; `go-systems-engineer` implements it; the Phase D.3 cross-platform invocation matrix is what actually proves it.

## YOUR TASK

**Build LordCode**: a standalone, multi-provider, agentic AI coding CLI **and team daemon**, written in Go, which embeds the complete `claude-global-library` and executes that library's full phase-gated SDLC pipeline.

There are **four** load-bearing components. Every one of them is a genuine engineering problem, not glue:

### 1. The whole library, compiled in — and the whole SDLC, run per requirement
This is the product. Everything else supports it.

**The corpus becomes code.** All **528 agents, 1034 skills, 104 domain knowledge graphs, 77 math masters, 9,146 typed edges, 368 mapped regulations** are code-generated into Go source and compiled into the binary (ADR-3). Not read from disk, not parsed at startup, not a curated subset. Nobody ever authors an agent or a skill again, because the complete capability set is already compiled in — and, because it is code rather than data, an agent missing one of its mandatory skills is a **build error** rather than a silent runtime hollow dispatch.

**And a requirement runs the whole pipeline, not one agent.** This is the part that separates LordCode from every tool in its category. Give Claude Code or Codex CLI a requirement and you get one model loop with your own prompt. Give LordCode a requirement and it runs the **full SDLC**: `business-analyst-agent` and `product-manager-agent` turn it into FRs with acceptance criteria → `solution-architect` produces an HLD with real ADRs → `consensus-agent` gates it BINARY → the domain specialists implement → `hallucination-detector` and `context-faithfulness-engineer` verify → the QA chain tests → the Phase F security chain audits → `reliability-auditor` computes RS = 1.0 → the Ops chain reviews readiness. **Realistically 40–80+ specialist invocations per requirement**, each one a grounded persona carrying its own M1–M6 derivations, worked examples, and operating rules — not one generalist prompted 80 times.

Measured corpus footprint (verified on disk 2026-09-04): `agents/` 8.5 MB + `skills/` 47.7 MB + `knowledge-graph/` 28.1 MB = **84.3 MB raw, 24.7 MB gzip -9**. Persona and skill text alone is 56.2 MB. These numbers drive ADR-3's storage form and are not negotiable downward without dropping capability.

**The one hard physical limit, stated plainly so nobody designs against it:** 56.2 MB of persona and skill text is roughly **14 million tokens**. No context window today holds it, so "every agent at once, in one context" is not achievable in any architecture — it is off by an order of magnitude. What IS achievable, and what LordCode does, is running every agent the requirement actually touches, **sequentially and in parallel groups across the pipeline**, each with its own bounded context per the Differential GSD budget. Completeness comes from the pipeline's breadth over time, never from one giant context window. Any design that assumes otherwise is wrong on arithmetic, not on taste.

**On token cost — explicit product decision, do not over-engineer this.** 40–80 agent invocations per requirement run on the *user's own* account, and that is accepted: **the user pays their own provider bill, and a thorough run costing real tokens is the point of the product, not a defect to optimise away.** Do NOT build spend ceilings, pre-run cost approval prompts, or budget-gated execution as MVP features. What LordCode DOES ship is simple visibility: after a run, show what it cost, broken down per phase. That is reporting, not a gate.

Nothing unsafe is lost by this. The runaway case — a loop that never terminates and drains an account — is already prevented structurally by the harness, where the hard `T_max` bound and the cumulative budget guard are **mandatory stop disjuncts** (see `harness-engineering-architect`'s dispatch). Runaway protection is a harness invariant that exists regardless; a user-facing cost ceiling was a separate convenience feature, and it is deliberately out of scope. `llm-cost-optimizer`'s CPST work remains in scope for the ROUTER's own optimisation objective — it is what makes routing pick well — not as a spending gate on the user.

### 2. Multi-provider model routing — any model, any account
LordCode does not lock the user to one vendor. **Three first-class named providers: OpenAI, Anthropic, and Google Gemini** — plus an adapter interface open to others. The user brings **whichever account they already have** (an OpenAI account, an Anthropic account, a Gemini account, or several at once) and LordCode works with all of them; there is no "primary vendor" and no degraded second-tier provider. Per task, a real router selects among them — cascade, contextual bandit, classifier, or embedding-similarity — chosen in ADR-1 on math, not preference, with `genai-routing-mathematician` deriving the regret bounds. Confidence gates, per-provider circuit breakers, and cost-per-successful-task optimisation are part of the router, not bolted on afterwards.

**The connect-your-account UX is the headline feature of this component.** The user experience is: *"Gemini account hai? connect it. OpenAI account hai? connect it. Claude account hai? connect it."* Add one, add all three, use whichever. `lordcode auth login <provider>` connects; `lordcode auth list` shows what is configured; the router then works with whatever the user actually has. A user with only a Gemini account gets a fully working tool — no provider is required, and no provider is privileged.

**⚠ One hard truth this UX must not paper over, or it breaks on first contact:** a consumer **subscription is not API access**. ChatGPT Plus does not grant OpenAI API access — that is billed separately and needs an API key with credits from `platform.openai.com`. Claude Pro/Max likewise does not grant Anthropic API access (`console.anthropic.com` is separate billing). Google Gemini is the friendliest of the three: a Google account can obtain an AI Studio API key, and a free tier exists. So the honest shape is: **"connect your account" as the UX surface, provider API credentials underneath, and an error message that says exactly what is missing** — "Your ChatGPT Plus subscription does not include API access; LordCode needs an API key with credits from platform.openai.com" is a good error, "authentication failed" is a product-destroying one. Phase 0 writes this as an FR; `technology-scout-analyst` verifies the current per-provider auth options (OAuth device flow vs API key paste) before the PRD claims anything specific.

**Design consequence:** the provider-adapter contract (Phase 1.5) must be genuinely provider-neutral. Three providers with three different streaming protocols, three tool-calling schemas, three error taxonomies, and three auth models is the real integration problem — and a design that treats one as the reference shape and the others as translations will accumulate bias toward that one. Per `genai-procurement-decision-core`, `C_format` (API-conversion cost) dominates switching cost at **40–60%**, so the adapter interface is where vendor lock-in is either avoided or silently created.

### 3. A real runtime harness / control loop
Agent-loop lifecycle, tool-call mediation, stop conditions, token-budget ceilings, retry/backoff, circuit-breaker thresholds, and deterministic replay for audit. This is what separates a reliable tool from a fragile prompt-chaining demo. Users must be able to ask *why did LordCode pick that model for that task, and what did it cost* — and get a real, replayable answer.

### 4. A full SDLC pipeline engine — the thing that actually engages the corpus
LordCode runs the library's own pipeline as a product feature: a phase state machine (Phase 0–8, A–G, Ops.1–5), per-gate evaluators (consensus BINARY, `RS = (NLI × FactScore × DRE × Coverage)^(1/4) = 1.0`, Phase F all-severities-zero, Phase H regression, PRR GO/NO-GO), the bounded SC.1–SC.3 self-correction loop, and the 23-node / 82-branch decision tree as a traversable runtime artifact. **This is effectively `ORCHESTRATION_TEMPLATE.md` compiled into an executable engine.**

**Two selections happen per requirement, and conflating them is the most likely architectural mistake in this build:**

| Selection | Owner | Question it answers |
|---|---|---|
| **WHICH AGENTS run** | SDLC pipeline engine (D39) | Which specialists does this requirement touch, in which phases, in what dependency order, under which gates? |
| **WHICH MODEL each runs on** | Multi-provider router (D23) | For this one agent invocation, is OpenAI, Anthropic, or Gemini the right model — given capability DNA, cost, latency, and which accounts the user actually has? |

These are orthogonal. The pipeline engine may dispatch `threat-modeling-specialist`; the router independently decides that invocation runs on Gemini because the user has no Anthropic key configured and Gemini scores above θ_min = 0.60 for adversarial reasoning. Neither owns the other's decision. The engine is what makes "all relevant agents get used" true; the router is what makes "any model, any account" true. `solution-architect` must specify this seam explicitly in the HLD, alongside the harness layering in Alignment 6.

### 5. Open to contributions
LordCode accepts external contributions. This is a product decision with real engineering consequences, not a README line: it requires a licence choice, `CONTRIBUTING.md`, a code of conduct, a documented PR review path, and — because this is a CRITICAL-security binary that handles multiple users' provider credentials — a **hardened contribution security model**: signed commits, mandatory review by a maintainer, CI that runs the Phase F.2 static-analysis and secrets-detection gates on every external PR before merge, and dependency-addition review. An open contribution model on a credential-handling tool is a supply-chain surface, and it must be designed as one. `security-lead-auditor` and `dependency-vulnerability-analyst` own that review path.

**Roadmap (state in README, do NOT build in v1):** LordCode's **own models** are a stated future direction. The v1 scope is strictly BYO-account routing across third-party providers — **no training, no fine-tuning, Domain 22 (Foundation Model) out of scope for this build.** The architectural obligation this creates today is narrow but real: the provider-adapter interface must not be shaped so that only third-party HTTP APIs can satisfy it, or a future first-party model becomes a rewrite instead of another adapter. **Explicit non-goals — do not silently expand into these:** no model training or fine-tuning in v1 (roadmap only, see above); LordCode does not broker or resell inference (OAQ-5: BYO key, free); it does not modify `claude-global-library`; and it does not implement a corpus-update mechanism (NEW-1: the library is frozen).

## ADR REGISTER — what is decided, what Phase 1 must still decide

### ADR-1 — Router topology · **OPEN, Phase 1 decides**
Genuinely open, with real math consequences. Candidates and their verified quantified tradeoffs (from `multi-model-routing-core`):

| Topology | Latency | Learning | Note |
|---|---|---|---|
| Rule-based cascade | ~0 ms | none | Break-even: cheap model wins whenever `c_cheap/c_expensive < q_cheap` (acceptance rate). At a 0.067 price ratio, cascade profits whenever `q₁ > 6.7%`. |
| Embedding-similarity KNN | ~5–20 ms | few-shot | **Constrained by ADR-2** — Go has no numpy/torch. Requires either an embedding API call on the routing hot path, or build-time-precomputed persona vectors with hand-rolled cosine similarity (tractable — it is dot products). |
| Classifier router | ~10–50 ms | supervised | Upfront task-type classification. |
| LinUCB / Thompson bandit | adaptive | online | Regret `O(d√T log T)`. |

Confidence-gate optimal threshold: `h(τ*) = (C_loss + C_esc) / (R + C_loss)` — ADR-1 must cite this formula explicitly. Every model in the pool requires its own circuit breaker (open at 50% failure over a 60 s window, 30 s half-open probe) — never one global breaker. A mandatory SPRT shadow-mode rollout (≥10% shadow traffic; boundaries `A = (1-β)/α = 18.0`, `B = β/(1-α) = 0.105` at α=0.05, β=0.10) precedes any router reaching full production.

**Explicit revisit trigger:** if ADR-1 lands on embedding-similarity or anything requiring on-device numerical work, **ADR-2 must be reopened** — this is the one topology Go genuinely constrains.

### ADR-2 — Backend implementation stack · **RESOLVED → Go**
**Status:** Accepted, 2026-09-04. Decided by a dispatched language-selection expert that read all four candidate `agent.md` files in full and scored 8 weighted criteria.

**Scores (weighted /1000):** **Go 885** · Rust 753 · Node+TS 718 · Python 718.

**Why Go — the three locked constraints each independently favour it, and they compound:**
1. **Library-as-code (ADR-3).** `go generate` is a first-class part of the stdlib toolchain, so compiling 528 agents and 1034 skills into typed Go source is the idiomatic path rather than a bolted-on build hack — and Go's compiler then enforces the library's core invariant for free: an agent referencing a nonexistent skill fails the build. (`//go:embed`, also stdlib since 1.16, remains available as the fallback storage form and is why either ADR-3 option is cheap here.) Rust could do this via proc-macros but their compile time degrades measurably at thousands of items; Node and Python have no compile step at which to catch a missing skill at all — the check would stay a runtime hook, which is exactly the weakness code generation is meant to remove.
2. **Daemon from v1 (ADR-6).** This is Go's design centre. `net/http` is stdlib and production-grade; provider fan-out is `errgroup` + `context` cancellation, the cleanest concurrency model of the four for this exact shape of work; `http.Server.Shutdown(ctx)` gives graceful drain free; `GOMEMLIMIT` (1.19+) gives a hard ceiling for a process living on a laptop for days. `go-systems-engineer`'s own Operating Rules 1 and 7 (*every goroutine has a documented exit condition*; *`context.Context` is the first parameter of anything that blocks*) are shaped precisely for long-lived-process failure modes.
3. **CRITICAL security.** The strongest supply-chain posture of the four by a wide margin: `go.sum` plus the **transparency-log-backed checksum database** (`sum.golang.org`) is a verification property no other candidate has by default; `govulncheck` performs *reachability* analysis rather than version matching, so findings are actionable rather than noise; and critically **Go modules execute no install-time scripts**, unlike npm and pip — decisive for a binary holding multiple providers' production credentials under CERT-In reporting obligations. Compounding win: `zalando/go-keyring` is **pure Go** (macOS Keychain, Windows Credential Manager via wincred, Linux Secret Service over D-Bus), so credential storage does **not** break a `CGO_ENABLED=0` static build.

Supporting ecosystem: Charm (Bubble Tea / Lip Gloss / Bubbles / Glamour) for the streaming terminal interface; `cobra` + `viper` as the de-facto CLI/config standard.

**Consequences — what Go costs, stated honestly:**
- **Second-tier provider SDKs.** `openai-go` and `anthropic-sdk-go` both exist and are Stainless-generated, but Python and TypeScript are the reference tier — new API surface (beta headers, prompt-caching helpers, tool-use runners) lands there first and reaches Go weeks-to-months later. Partially moot, since a multi-provider router needs its own normalised abstraction anyway and would be wrapping vendor SDKs regardless — but **budget for a standing provider-adapter maintenance burden** Node or Python would not incur.
- **Verbosity in the router core.** No sum types, no exhaustive `match`. Modelling heterogeneous provider responses, routing decisions, and stop conditions is genuinely uglier than in Rust or TypeScript.
- **`embed.FS` stores assets uncompressed.** The raw 84.3 MB corpus would produce a ~90 MB+ binary. → ADR-3's mitigation is mandatory, not optional.
- **Cold-start indexing, not embedding, is the real cost.** Having the files is free; *parsing* 528 `agent.md` files plus the Master KG JSON is not. → ADR-3.
- **Three library capability gaps** — see the CAPABILITY GAP REGISTER below.

**Rejected — Rust (753):** genuine wins (no GC ⇒ flat multi-day RSS; `cargo-vet` chained human audits) but neither is a v1 blocker for an I/O-bound local tool whose hot path waits on HTTPS. Paradoxical supply-chain position — best tooling, worst raw surface (a tokio + reqwest + ratatui app routinely pulls 300–500 transitive crates, and `build.rs` + proc-macros execute arbitrary code at build time). **Disqualifier: no official Anthropic Rust SDK is known to exist**; community-only OpenAI support. For a product whose entire differentiator is multi-provider routing, starting from zero vendor support is a self-inflicted wound. Slowest iteration and hardest cross-compilation matrix of the four.

**Rejected — Node.js + TypeScript (718), the closest call:** wins two axes outright — provider SDKs (10/10, the reference tier) and iteration speed (9.5/10) — and it is what the category incumbents ship on, which is evidence rather than fashion. Loses on **precisely the axis flagged CRITICAL**: npm install-script execution plus tree depth, in a binary holding multiple users' provider credentials, under CERT-In breach-reporting obligations, is the hardest thing here to defend after an incident. Compounding: the standard keychain library `keytar` is **archived and unmaintained**, and its successors are native modules that fight every single-binary path; and there is no credible single-binary story (`pkg` unmaintained, Node SEA still experimental, Bun `--compile` means committing to a non-Node runtime).

**Rejected — Python (718):** same SDK strength as Node, *better* keychain (`jaraco/keyring` is the mature reference implementation) and better supply chain than npm; Textual + Rich are arguably the finest terminal-rendering libraries in any language. But distribution is the worst of the four — PyInstaller/Nuitka produce large, slow-starting, per-platform artifacts that routinely trip Windows antivirus heuristics, a fatal first-impression problem for a developer tool. Interpreter startup (100–400 ms before any indexing) is a poor fit for something invoked dozens of times a day, and long-lived Python daemons on end-user laptops are the weakest daemon story here.

### ADR-3 — Library-consumption mechanism · **RESOLVED → full embed; Phase 1 designs the HOW**
**Decision:** the complete library is vendored into the LordCode build artifact. Not a curated subset, not a filesystem reference, not a published package. The whole point of the product is that the capability set is complete and present.

**Measured, verified on disk 2026-09-04:**
| Tree | Raw |
|---|---|
| `agents/` (529 dirs) | 8.5 MB |
| `skills/` (1035 dirs) | 47.7 MB |
| `knowledge-graph/` (104 domain KGs + `_master`) | 28.1 MB |
| **Total** | **84.3 MB raw → 24.7 MB gzip -9** |

**The mechanism is CODE GENERATION, not file embedding — this is decided, not open.** The markdown corpus is a *build input*, not a runtime artifact. A `go generate` step walks `LIBRARY_PATH` and emits Go source: every agent becomes a typed value carrying its persona text, its resolved skill set, its KG route, and its model tier; every skill becomes a value carrying its content; every KG edge set becomes a Go data structure rather than JSON to unmarshal. The generated source is compiled into the binary. At runtime LordCode reads no markdown, parses no JSON, and inflates no cache directory to resolve a persona.

**Why code generation rather than `embed.FS` + runtime parse — the decisive reason is not performance:**
- **Compile-time validation of the library's own core invariant.** The library's `agent_persona.py` hook exists to block a "hollow persona" — an agent dispatched without its mandatory skills. As generated code, that check moves from a runtime hook to the **type system**: an agent whose `skills:` frontmatter names a skill that does not exist becomes a *build error*, not a silent runtime failure. A hollow dispatch stops being possible to ship.
- **Zero startup cost.** No parse of the 925 KB `agents_all.json`, the `skills_all.json`, or the 3.36 MB `edges_all.json`. The library's own `CLAUDE.md` notes that reading those wholesale to route one task is "~99% waste" — code generation removes the read entirely rather than optimising it.
- **No cache directory, no inflation step, no first-run latency, no partial-write failure mode** on a corpus this size.

**What Phase 1 must still decide (the genuinely open part of ADR-3) — the STORAGE FORM of the generated payloads.** Both candidates keep the typed structs and the compile-time validation; they differ only in how the 56.2 MB of persona/skill text is carried:

| Form | Binary size | Access cost | Generated-source cost |
|---|---|---|---|
| **(a) Plain Go string constants** | ~90 MB+ (Go stores string constants uncompressed, exactly like `embed.FS`) | Zero — a slice into the data section | 56 MB of literals must be split across many files; long compile times |
| **(b) Per-item gzip-compressed byte slices** | ~25–30 MB | One decompress per persona/skill access, cacheable in memory for the process lifetime | Smaller, less readable generated source |

Form (b) is the more likely answer given that the daemon (ADR-6) can decompress once and hold the working set in memory for the process lifetime, which turns the access cost into a per-daemon-start cost — a third independent argument for the daemon decision. But solution-architect must decide it on measured numbers from `go-systems-engineer`, not on this document's expectation. Whichever form wins, **the direction is locked: the library becomes compiled code, not embedded data.**

**Consequence, and why it is acceptable here:** compiled-in personas cannot be hot-updated without a rebuild and release. Under NEW-1 (**the library is frozen and will not be updated**) that is a non-issue for the MVP, and no refresh mechanism is in scope. A `library_version` stamp (`v29.96.2`, built `2026-08-29`) is compiled in for provenance and surfaced by `lordcode --version`. **If that assumption ever changes**, an overlay design (compiled corpus as the floor, an updated corpus layered over it at runtime) is the migration path — record it as a future ADR, do not build it now.

### ADR-4 — Credential storage · **OPEN, Phase 1 decides; security holds veto**
Candidates: OS keychain, encrypted config file, env-var-only, or a server-side secret store for the multi-user daemon. Verified starting point: **`zalando/go-keyring` over `99designs/keyring`** unless file/`pass` backends are needed on day one — the pure-Go implementation preserves `CGO_ENABLED=0`.

**The part that needs real design work, not an afterthought:** headless Linux (SSH, containers, CI) has no running Secret Service, so a fallback is required — an encrypted file with a passphrase- or OS-derived key. **That fallback is exactly where DPDP §4 and CERT-In scrutiny will land.** Separately, the multi-user daemon needs per-user credential isolation with a documented blast radius: `cloud-security-core`'s least-privilege score `|permissions_used| / |permissions_granted|` targets **> 0.8**. `secrets-detection-specialist` (D19) owns the secrets-never-in-logs requirement. Per STEP 10.5, **security has veto power over this ADR at Phase F**, not merely advisory input.

### ADR-5 — Distribution / packaging · **DEFERRED (OAQ-3), Phase 1 decides**
Deferred deliberately: Go *widens* this decision rather than narrowing it. Open channels: GitHub Release binaries, Homebrew, Scoop/winget, apt/rpm/AUR, `go install`, Docker, **and npm** (a thin npm wrapper that downloads the platform-appropriate binary is a well-worn pattern — the npm audience without the npm dependency tree). Choosing Node would have *closed* every single-binary channel.

**Forced cost of shipping binaries:** macOS notarization and Windows Authenticode signing become your problem — budget an Apple Developer account and a code-signing certificate. `release-engineering-specialist` (verified, D-release) owns this ADR.

### ADR-6 — Daemon / server mode · **RESOLVED → IN SCOPE v1, network-exposed team server**
This is the largest scope decision here. Consequences, all of which propagate through the rest of this document:
- **Phase 1.5 produces a literal `openapi.yaml`** for the daemon surface, in addition to the CLI command contract and the provider-adapter contract.
- **Scale becomes multi-tenant.** Per-user authn/authz, per-user credential isolation, per-user context isolation (DPDP §4), and rate limiting are MVP requirements, not fast-followers. `api-design-core`'s M2 rate-limiting algorithms (token bucket vs sliding window) are load-bearing.
- **Security Risk → CRITICAL**, Phase F at FULL depth including F.3 (dynamic/API — a live target now exists) and F.4 (infrastructure/crypto).
- **Full Ops.1–Ops.5** at Tier 2–3 depth: real SLOs, error budgets, DR tiers, bake time, on-call.
- **A polyglot split becomes nearly free, and should be taken.** The eval/replay harness is data-science-shaped work where Go is weakest and Python strongest. Because the daemon already exposes an HTTP/OpenAPI surface, the harness can be a **separate Python tool driving the daemon over that API**. **Design consequence: treat the daemon's OpenAPI surface as a first-class, stable integration contract from day one** — LordCode's own tooling will be its first external consumer.

### ADR-7 — SDLC pipeline engine · **OPEN, Phase 1 decides — NEW, has no v1 counterpart**
Introduced by NEW-2. LordCode must execute the library's full phase-gated SDLC. Phase 1 must design:
- a **phase state machine** covering Phase 0–8 and A → A.5 → A.6 → B → C → D → H → F → E → G → Ops.1–5;
- **per-gate evaluators**: consensus BINARY, `RS = (NLI × FactScore × DRE × Coverage)^(1/4) = 1.0`, Phase F all-severities-zero, Phase H (zero regressions, pass-rate ≥ 0.98 over 5 replays, McNemar p > 0.05, Krippendorff α ≥ 0.80), PRR GO/NO-GO;

Open question ADR-7 must answer: is the pipeline **hardcoded** in Go, or **interpreted** from the embedded decision-tree/template artifacts? The interpreted design keeps LordCode's pipeline faithful to the library it embeds; the hardcoded design is simpler and faster. This is a genuine architectural fork — do not pre-select it here.
